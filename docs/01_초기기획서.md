## 1. 배경

데이터 엔지니어(DE) 직무에서 보는 역량은 도구를 설치해 본 경험이 아니라 다음과 같습니다.

- 데이터를 **유실·중복 없이** 받는가
- 늦게 오거나 잘못된 데이터를 **조용히 버리지 않고** 처리하는가
- 같은 작업을 다시 돌려도 **결과가 같은가** (멱등성)
- 장애가 나도 **복구되고, 그 사실이 기록되는가**
- 운영 중 상태를 **수치로 지켜볼 수 있는가** (모니터링)
- 모델이 어떤 데이터로 학습됐는지 **추적·재현되는가**

이 프로젝트는 이 역량을 실제 실시간 데이터로 보여주는 것이 목적입니다. 데이터 소스는 업비트입니다. 키 없이 24시간 시세를 받을 수 있고, 공식 1분 캔들이 있어서 **직접 만든 집계가 맞는지 외부 기준으로 채점할 수 있기 때문**입니다.

## 2. 목표

### 한 문장 목표
업비트 KRW 전체 마켓의 실시간 시세를 유실·중복 없이 받아 Bronze → Silver → Gold로 정리하는 파이프라인을 만들고, **2주 동안 연속 운영하며 모니터링으로 상태를 수치로 보여준 뒤**, 그 2주 데이터로 코인별 "다음 5분 급변동 확률" 예측이 되는지 확인한다.

### 세부 목표
| # | 목표 | 증거 |
|---|---|---|
| G1 | 실시간 수집 (수집기 2대 → Kafka 3대 → Spark → Delta) | 2주 운영 기록 |
| G2 | Bronze → Silver → Gold 정제와 스타 스키마 | 테이블 명세, 건수 대사(Bronze = Silver + 격리 + 중복), 품질 검사 결과 |
| G3 | 정확성 | 공식 1분 캔들과의 일치율 |
| G4 | 신뢰성 | 장애 시험(T01~T17 중 해당분) 결과, 복구 시간, 공백 기록 |
| G5 | 모니터링 | Grafana로 수집량·지연·적체·격리·디스크·메모리를 보고 경보를 받음 |
| G6 | ML 확인 | 2주 데이터로 학습·평가한 결과를 기준선(B0, B1)과 비교 |
| G7 | 화면 | 운영 대시보드(Grafana), 데이터 확인 화면(FastAPI + React) |

## 3. 범위

### 포함
- 대상: KRW 마켓 전체 코인 (2026-11-25 기준 301개)
- 데이터: 체결, 호가(30단계), 현재가, 마켓 목록·주의 표시, REST 1분 캔들(대사·공백 보충)
- 저장: 2주 수집분 전부를 Delta(Bronze/Silver/Gold)에 보관. PostgreSQL은 화면용 최근 복사본
- 예측(ML 단계): 코인별 다음 5분 변동폭이 그 코인의 평소 기준을 넘을 확률. 거래가 충분한 5분 구간만 라벨·채점

### 제외
- 주문, 자동매매, 투자 판단, 수익률 주장
- 가격 방향(오를지 내릴지) 예측
- 대용량 처리 주장 (규모보다 정확성과 운영을 보여줌)
- 백업, 장비 이중화(PC 1대), 클라우드 배포
- 수집 데이터·데이터셋·모델 파일 공개

## 4. 데이터 이용 원칙

업비트 약관을 직접 확인한 결과입니다(2026-11-25, [09 문서 M10](09_결정현황.md)). 법률 판단이 아니라 약관 문구에 맞춘 운영 원칙입니다.

| 원칙 | 근거 |
|---|---|
| 수집 원본과 가공 데이터셋은 공개하지 않음 | Open API 약관 제5조: 데이터 저작권은 두나무에 있고 무단 복제·배포 금지 |
| 영리 목적으로 쓰지 않음 | Open API 약관 제5조, 업비트 약관 제10조 |
| 업비트 로고·서비스 화면 캡처를 문서에 쓰지 않음 | 업비트 약관 제11조 제4항: 사전 서면 허락 필요 |
| 요청 수 제한을 지킴 (`Origin` 헤더 없음, 재연결 대기, REST 초당 10회 미만) | Open API 약관 제6조 제2항, 요청 수 제한 문서 (M9) |
| **[제안]** 공개는 코드, 문서, 우리 시스템의 지표(유실·중복·일치율·지연·복구 시간·모델 성적)만. 출처를 "업비트 Open API 시세"로 표기하고 비상업 개인 프로젝트임을 밝힘 | 약관에 비상업 개인 분석과 요약 지표 공개를 다루는 명시 조항이 없음. 확실히 하려면 업비트에 문의 |
| **[제안]** 가격 차트 화면은 공개하지 않거나, 공개 전에 업비트에 문의 | 차트는 데이터를 그대로 보여주는 것이라 배포로 볼 여지가 있음 (미확인) |

## 5. 성공 기준

핵심 기준(①②)은 통과·실패를 판정하고, 보조 기준(③④)은 측정값으로 보고합니다(장애 시험은 시험별 판정). 호가는 공식 기준이 없어 유실 판정 대신 공백 창을 보고합니다.

| 기준 | 목표 | 비고 |
|---|---|---|
| 연속 운영 | 2주(14일, 달력 기준) | 공백이 생겨도 실패가 아니라, 모든 공백이 기록되고 원인이 설명되면 통과. 계획 정지(PC를 꺼야 할 때)는 정지 절차를 거치고 기록. 큰 장애가 나도 다시 시작하지 않고 장애 보고서를 씀 |
| ② 공식 캔들 일치율 (핵심) | 개발 기간 측정 후 2주 시작 전에 고정 | 공식 캔들이 있는 분 기준. 전체와 마켓×1시간 칸 최소값. KRW-BTC 3분 사전 시험은 100% 일치 |
| ① 체결 유실 (핵심) | 수집기가 하나라도 살아 있던 구간에서 0건 | 공식 캔들 대사로 판정. 둘 다 끊긴 구간은 공백으로 기록 |
| ① 중복 (핵심) | Silver에서 `(market, sequential_id)` 기준 0건 | |
| 호가 공백 (보고) | 공백 창의 횟수와 총 분 | 대조할 공식 기준이 없어 판정하지 않음 |
| 재실행 멱등성 | 같은 입력 재계산 시 결과 해시 동일 | |
| ③ 지연 (보조) | 개발 기간 측정 후 2주 시작 전에 고정 (수신 → 저장 p95) | 시계 동기화 확인 필요 |
| ③ 경보 도착 (보조) | 수집 중단·디스크 부족·테이블 정지가 경보로 옴 | Discord. 장애부터 경보 도착까지 걸린 시간을 기록 |
| ④ 장애 시험 (보조, 시험별 판정) | 06 문서의 DE 시험 통과, 복구 시간 기록 | 데이터 시험(T01~T05)은 개발 기간, 정지·장애 시험은 2주 중 정해 둔 시각에 실행 |
| ML | 기준선 대비 결과를 정직하게 기록 | 기준선을 못 이겨도 실패가 아님 |

## 7. 운영 규칙

| 규칙 | 이유 |
|---|---|
| 2주는 1~5단계가 모두 돌고, 경보가 실제로 오는지 시험한 뒤 시작 (확정) | 개발 중에는 재시작이 잦아 "연속" 기록이 의미 없음. 그 시점의 지연·메모리 기록은 나중에 만들 수 없음 |
| 개발 기간 데이터는 2주 시작 전에 삭제 (확정) | 디스크 여유 30%까지 전체 약 59일(계산, Kafka 3일 보관). 개발 데이터에는 공백·중복이 섞여 ML에 쓰기도 애매함 |
| 2주 동안 코드 고정. 버그 수정만, 언제·무엇을·왜 고쳤는지 기록 (확정) | 결과가 어느 코드 버전에서 나왔는지 분명해짐 |
| 수집기는 종류별 연결 3개로 받고, 5분마다 마켓 목록을 직접 확인해 바뀌면 구독을 다시 보냄 (확정) | 2주 안에 상장·폐지가 생기면 새 코인이 빠짐 |

### 2주 동안 PC 사용

파이프라인이 도는 동안에도 PC는 평소처럼 쓸 수 있습니다. 메모리는 전체 31.2GB(실측) 중 파이프라인 약 9~18GB(추정)를 빼고 약 13~22GB가 남습니다(계산, 1단계에서 실측). 파이프라인은 GPU를 쓰지 않습니다. 아래는 **2주 운영 기간에만** 지킵니다. 개발 기간 데이터는 지우므로 상관없습니다.

| 하면 안 되는 것 | 이유 |
|---|---|
| PC 끄기·재시작·절전 | 전체가 멈춤. 꺼야 하면 계획 정지 절차를 따름. 절전은 이미 꺼져 있음(실측) |
| Docker Desktop 종료, 업데이트 후 재시작 | 컨테이너가 전부 멈춤. 업데이트는 2주 뒤로 미룸 |
| `wsl --shutdown`, WSL 종료 | 전체가 멈춤 |
| 메모리를 거의 다 쓰는 작업 | 파이프라인이 느려지거나 멈출 수 있음 |

## 7-1. 다른 공개 프로젝트에서 가져온 것

비슷한 업비트 공개 프로젝트를 읽고 Airflow 일일 배치, 마켓 × 1시간 대사, 죽은 연결 감지, 수집기 디스크 버퍼, 체결 재수집 확인, 거래 없음과 유실 구분, 조용한 멈춤 감시, 회고 방식을 가져왔습니다. 목록과 이유는 [09 문서 9-2절](09_결정현황.md)에 있습니다.

## 8. 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| WSL 메모리 한도 15GB (실측) vs 추정 9~18GB | 컨테이너 강제 종료 | 1단계에서 실측하고 필요하면 `.wslconfig`로 상향 (Claude 위임) |
| 집 인터넷·정전 | 수집기 2대가 같이 끊김. 호가는 메울 수 없음 | 공백 기록, REST로 1분 캔들만 보충, 보고서에 명시 |
| 업비트 연결 장시간 유지 여부 미확인 | 예상 못 한 끊김, 연결은 열려 있는데 데이터가 안 오는 상태 | 0단계에서 하루 이상 연결 시험, 데이터가 끊기면 다시 연결, 공백 기록 |
| Kafka 쓰기 불가 | 호가는 되돌릴 수 없어 영구 유실 | 수집기 로컬 버퍼 (T19) |
| 파이프라인이 조용히 멈춤 | 며칠 동안 모름 | 테이블 신선도 검사, 긴급 경보 채널 |
| 업비트 요청 수 제한 | 429·418 차단 | `Origin` 헤더 없음, 재연결 대기 시간 증가, REST 초당 10회 미만 |
| 새 상장·폐지 코인 | 대상 누락 | 마켓 목록 변화 시 재구독 |
| SSD 고장 | 데이터 손실 | 백업하지 않음. [10_한계.md](10_한계.md)에 기록 |
| 디스크 부족 | 수집 중단 | 2주 약 295GB, 여유 약 62% 남음(계산, Kafka 3일). 30% 경보 |
| 약관 해석 | 공개 범위 문제 | 4절 원칙, 불확실한 것은 공개하지 않거나 업비트에 문의 |
| 예측 성능이 낮음 | ML 결과가 약해 보임 | 핵심 증거는 파이프라인 운영. 기준선 대비 결과를 그대로 보고 |
