# 07. 단계별 실행 계획

원칙: **도구를 먼저 다 깔지 않는다. 데이터부터 보고, 한 단계씩 돌아가는 것을 만든 뒤 다음 도구를 붙인다.** 각 단계는 끝나면 그 자체로 동작하는 결과물이 남습니다.

| 단계 | 내용 | 기간 (추정) | 결과물 |
|---|---|---|---|
| 0 | 데이터 프로파일링 | 2~3일 | 데이터 프로파일 (`notes/00_data_profile.md`) |
| 1 | Kafka → Spark → Bronze | 1~2주 | 24시간 수집되는 Bronze 테이블 |
| 2 | Silver | 1~2주 | 중복 제거·불량 격리된 Silver 테이블 |
| 3 | Gold + 대사 + Grafana | 1~2주 | 스타 스키마, 공식 캔들 일치율, 운영 대시보드 |
| 4 | AI-ready 데이터셋 | 1주 | 누수 검사를 통과한 버전 관리 학습셋 |
| 5 | 학습 + MLflow | 1주 | 기준선 대비 모델 비교 결과 |
| 6 | 실시간 예측·채점·재학습 | 2~3주 | 예측 → 채점 → 재학습 → 승격 루프 |
| 7 | 이중화·장애 시험 | 1~2주 | 장애 시험 결과 (T11~T17) |

---

## 0단계. 데이터 프로파일링

**Kafka도 Spark도 쓰지 않습니다. Python만 씁니다.**

할 일
- [ ] WebSocket에 연결해 상위 10개 마켓의 체결·호가를 30분 동안 `.jsonl` 파일로 저장하는 스크립트
- [ ] 저장 중 일부러 연결을 끊었다 다시 붙여 보기
- [ ] pandas 또는 DuckDB로 파일을 열어 1분 캔들 직접 계산
- [ ] 업비트 REST 1분 캔들과 비교 (3분 사전 시험은 완료, 10개 마켓·30분으로 확대)
- [ ] 대상 마켓 10개 확정 (거래대금 기준, 확정 후 고정)

답할 질문 (결과는 `notes/00_data_profile.md`에 기록)
- 마켓별 1분당 체결 수, 호가 메시지 수는?
- 체결 시각과 수신 시각의 차이(지연) 분포는? → watermark 초기값 결정
- 재연결하면 같은 체결이 다시 오는가? 몇 건이나?
- 체결이 없는 분이 있는가?
- 호가 단계 수는 몇 개인가? → **30단계 확인** (2026-11-24)
- 하루 수집 용량은? → 2분 표본으로 원본 약 11GB, 압축 후 약 1GB 추정. 30분 측정으로 다시 확인
- 5분 변동폭(`future_range`) 분포는? → 라벨 임계값 20%가 적절한지

완료 기준: 위 질문에 숫자로 답한 프로파일 문서.

## 1단계. Kafka → Spark → Bronze

할 일
- [ ] Docker Compose: Kafka 1대 (KRaft), Spark (local 모드)
- [ ] Producer: 0단계 스크립트를 Kafka 발행으로 변경, 봉투 형식([04 문서 2절](04_데이터명세서.md)), 재연결, 공백 기록
- [ ] Market Poller: 5분마다 마켓 목록 발행 (KRW 전체)
- [ ] Spark Structured Streaming: Kafka → `bronze_*_raw` Delta 테이블, 체크포인트 설정
- [ ] 압축·보관 설정: Kafka `compression.type=zstd`와 보관 7일, Delta 압축 코덱 zstd ([ADR-15](08_결정기록_ADR.md))
- [ ] **24시간 연속 수집 시작 → 이후 계속 켜 둠 (30일 운영의 시작)**
- [ ] 메모리 사용량과 하루 디스크 사용량 실측, [03 문서 5.1절·9절](03_시스템아키텍처.md) 갱신

시험: T06(수집기 장애), T07(Spark 잡 장애)
