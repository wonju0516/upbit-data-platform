# 07. 단계별 실행 계획

원칙: **도구를 먼저 다 깔지 않는다. 데이터부터 보고, 한 단계씩 돌아가는 것을 만든 뒤 다음 도구를 붙인다.** 각 단계는 끝나면 그 자체로 동작하는 결과물이 남습니다. 순서는 [09 문서 1절](09_결정현황.md)을 따르고, 이 문서와 다르면 09가 우선합니다.

| 단계 | 내용 | 결과물 |
|---|---|---|
| 0 | 데이터 프로파일링 | 데이터 프로파일 (`notes/00_data_profile.md`) |
| 1 | 수집기 → Kafka 3대 → Bronze | 계속 쌓이는 Bronze 테이블 |
| 2 | Prometheus + Grafana | 수집 상태·시스템 자원을 보는 운영 대시보드 |
| 3 | Silver | 중복 제거·불량 격리·호가 요약된 Silver 테이블 |
| 4 | Gold + 공식 캔들 대사 | 1분 캔들, 호가 1분 요약, 일치율 |
| 5 | PostgreSQL → FastAPI → React | DE용 `serve_*` 4개와 데이터 확인 화면 |
| 6 | **2주(14일) 연속 운영** + 장애 시험 | 운영 보고서 |
| 7 | 2주 데이터로 ML 확인 | 기준선 대비 결과 |
| 8 | 문서 정리, 종료 | README 핵심 수치, 최종 문서 |

기간은 근거 없는 추정이라 적지 않습니다. 2주 운영은 1~5단계가 모두 돌고 경보 시험을 마친 날부터 셉니다. 그 전에 받은 데이터는 개발용이라 시작 전에 지웁니다 ([09 문서 1절](09_결정현황.md)).

## 0단계. 데이터 프로파일링

**Kafka도 Spark도 쓰지 않습니다. Python만 씁니다.**

할 일
- [ ] WebSocket에 연결해 KRW 전체 마켓의 체결·호가·현재가를 30분 동안 `.jsonl` 파일로 저장하는 스크립트
- [ ] 저장 중 일부러 연결을 끊었다 다시 붙여 보기
- [ ] pandas 또는 DuckDB로 파일을 열어 1분 캔들 직접 계산
- [ ] 업비트 REST 1분 캔들과 비교 (KRW-BTC 3분 사전 시험은 완료, 여러 마켓·30분으로 확대)

답할 질문 (결과는 `notes/00_data_profile.md`에 기록)
- 마켓별 1분당 체결 수, 호가 메시지 수는?
- 체결 시각과 수신 시각의 차이(지연) 분포는? → watermark 초기값 결정 (PC 시계 동기화 상태도 함께 확인)
- 하루 이상 연결을 유지하면 업비트가 끊는가?
- 한 구독에 KRW 전체 코인을 넣어도 되는가? 구독을 바꾸는 순간 빈틈이나 SNAPSHOT 중복이 생기는가?
- 공백 구간의 체결을 REST 체결 이력으로 다시 받을 수 있는가? 며칠 전까지 되는가? (되면 공백 보충을 체결 단위로)
- 재연결하면 같은 체결이 다시 오는가? 몇 건이나?
- 체결이 없는 분은 마켓별로 얼마나 되는가?
- 호가 단계 수는 몇 개인가? → **30단계 확인** (2026-11-24)
- 하루 수집 용량은? → KRW 전체 계산값 Bronze 하루 약 12.2GB(압축 후). 30분 측정으로 다시 확인

완료 기준: 위 질문에 숫자로 답한 프로파일 문서.

## 1단계. 수집기 → Kafka → Bronze

할 일
- [ ] Docker Compose: Kafka 3대 (KRaft, RF=3, min.insync.replicas=2), Spark (local 모드)
- [x] 수집기(1대, 09 D7): 0단계 스크립트를 Kafka 발행으로 변경, 봉투 형식([04 문서 2절](04_데이터명세서.md)), 재연결, 공백 기록, 체결 REST 보충 (#7)
- [x] 연결 구성: 체결·호가·현재가 연결 3개
- [ ] 상장·폐지 반영: 5분마다 REST 마켓 목록 확인, 바뀌면 같은 연결에 구독 메시지 다시 보냄
- [ ] 죽은 연결 감지: 데이터가 일정 시간 오지 않으면 다시 연결
- [x] 로컬 버퍼: Kafka에 못 쓰는 동안 파일에 쌓고 복구 후 전송 (T19 통과)
- [x] 업비트 요청 수 제한 준수: `Origin` 헤더 없음, 재연결 대기 시간 증가
- [x] Market Poller: 5분마다 마켓 목록 발행 (KRW 전체, 수집기 안에서 실행)
- [ ] Spark Structured Streaming: Kafka → `bronze_*_raw` Delta 테이블, 체크포인트 설정
- [ ] 압축 설정: Kafka `compression.type=zstd`, Delta 압축 코덱 zstd. Kafka 보관 3일, 파티션은 체결·호가·현재가 3칸, 작은 토픽 1칸. 토픽은 자동 생성하지 않고 미리 만듦
- [ ] 연속 수집 시작
- [ ] 메모리 사용량과 하루 디스크 사용량 실측, [03 문서 5.1절·9절](03_시스템아키텍처.md) 갱신. WSL 한도(15GB)가 모자라면 `.wslconfig`로 상향

시험: T06(수집기 장애), T07(Spark 잡 장애), T12·T13(Kafka 브로커 장애), T18(데이터 없는 연결), T19(Kafka 쓰기 불가 중 호가)
