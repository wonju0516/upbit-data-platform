# 08. 결정 기록 (ADR)

각 결정마다 **검토한 대안, 고른 이유, 바꿀 조건**을 적습니다. 평가 표의 ●는 이 프로젝트 조건(소스 1개, 1인, 분석과 ML 두 소비자)에서의 상대 평가이며 측정값이 아닙니다.

## ADR-01. 정제 계층 구조

| 방식 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 원본 → 마트 2단계 | 단순 | 정제 규칙이 바뀌면 원본부터 다시 처리해야 함 | 탈락 |
| Lambda (배치·스트림 별도 코드) | 배치가 정확성 보장 | 같은 로직을 두 번 구현, 결과가 어긋날 수 있음 | 탈락 |
| Kappa (스트림만) | 코드가 하나 | 늦은 데이터를 고치려면 전체 재생 필요 | 부분 채택 |
| **Medallion + 일일 재계산** | 계층별 책임이 분명, Bronze에서 언제든 재처리. Spark 하나로 스트림과 배치를 같은 코드로 | 저장 공간이 계층 수만큼 늘어남 | **채택** |

**결정.** 실시간 경로는 하나(Kappa 방식)만 두고, 정정은 같은 Spark 변환 함수를 배치 모드로 다시 실행합니다. Lambda의 정확성을 얻으면서 코드를 두 벌 관리하지 않습니다.
**바꿀 조건.** 데이터가 작아서 Silver와 Gold를 나눌 이득이 없다는 것이 측정되면 계층을 합칩니다.

## ADR-02. Gold 모델링

| 방식 | 쿼리 단순성 | ML 친화성 | 변경 유연성 | 1인 구축 비용 | 판단 |
|---|---|---|---|---|---|
| **스타 스키마** | ●●● | ●●○ | ●●○ | ●●● | **분석 Gold** |
| 스노우플레이크 | ●○○ | ●○○ | ●●○ | ●●○ | 탈락 |
| **넓은 표 (OBT)** | ●●● | ●●● | ●○○ | ●●● | **ML Gold (스타에서 파생)** |
| Data Vault 2.0 | ●○○ | ●○○ | ●●● | ●○○ | 탈락 |
| 3NF (Inmon) | ●○○ | ●○○ | ●●○ | ●○○ | 탈락 |

- **스타 스키마**: 분석 질문이 대부분 "어떤 마켓의, 어떤 시간대에, 얼마나"라서 팩트 하나에 차원을 붙이는 구조와 그대로 맞습니다.
- **스노우플레이크 탈락**: 마켓은 수백 행이라 차원을 정규화해도 아끼는 것이 거의 없고 조인만 늘어납니다.
- **넓은 표는 파생물로**: 학습에는 한 행에 모든 피처가 있는 표가 편하지만, 이것을 원천으로 삼으면 차원 정보가 중복되고 수정이 어렵습니다. 원천은 스타 스키마에 두고 넓은 표는 언제든 다시 만듭니다.
- **Data Vault 탈락**: 소스가 많고 자주 바뀌는 기업 환경용입니다. 소스 하나를 혼자 다루기에는 관리 비용이 큽니다.

**바꿀 조건.** 해외 거래소 등 소스가 여러 개로 늘고 소스 간 이력 추적이 중요해지면 Silver와 Gold 사이에 Data Vault를 검토합니다.

## ADR-03. 테이블 포맷

| 포맷 | 장점 | 단점 | 판단 |
|---|---|---|---|
| Parquet만 | 가장 단순 | 쓰다 죽으면 반쪽 데이터가 보임, MERGE 불가, 버전 없음, 스트리밍 시 작은 파일 누적 | 탈락 |
| **Delta Lake** | Parquet + 트랜잭션 로그. MERGE, 타임 트래블, 스트리밍 sink exactly-once, Spark와 통합 쉬움 | Spark 밖 엔진의 쓰기 지원은 상대적으로 제한적 | **채택** |
| Iceberg | 엔진 중립적, 파티션 진화 | 카탈로그를 따로 띄워야 해서 초기 설정이 많음 | 후보 |
| Hudi | upsert 중심에 강함 | 설정 항목이 많음 | 탈락 |

**결정.** Delta Lake. 데이터는 그대로 Parquet 파일이고, 그 위에 변경 기록(`_delta_log`)이 붙습니다. 학습셋 버전 관리를 타임 트래블로 해결할 수 있습니다.
**바꿀 조건.** Trino 등 여러 엔진에서 같은 테이블에 쓰는 요구가 생기면 Iceberg로 옮깁니다.

## ADR-04. 처리 엔진

| 엔진 | 특징 | 판단 |
|---|---|---|
| **Spark Structured Streaming** | 마이크로배치(지연 수 초). 같은 코드로 스트림과 배치 처리 | **채택** |
| Flink | 이벤트 단위 처리, 지연이 가장 짧음 | 1분 단위라 불필요 |
| Kafka Streams | 가벼움, Kafka → Kafka 처리에 적합 | Delta 쓰기·배치 재계산에 맞지 않음 |

**결정.** 일일 재계산과 백필을 같은 코드로 할 수 있다는 점이 ADR-01과 맞물립니다.
**바꿀 조건.** 초 단위 이하 경보가 요구되면 그 경로만 Flink를 검토합니다.

## ADR-05. Kafka 설계

| 항목 | 값 | 이유 |
|---|---|---|
| 토픽 | `upbit.trade.raw`, `upbit.orderbook.raw`, `upbit.ticker.raw`, `upbit.market.raw`, `gold.candle_1m`, `predictions.vol_5m` | 종류별로 스키마와 처리량이 다름 |
| 키 | 마켓 코드 | 같은 마켓은 같은 파티션 → 마켓 안의 순서 유지 |
| 파티션 | 체결·호가·현재가 3개, 마켓 목록·공백 기록 1개 (2026-11-25 확정) | 브로커 3대가 1칸씩 리더를 맡음. 칸은 줄일 수 없어 작게 시작하고 2주 동안 바꾸지 않음 |
| Producer | `acks=all`, `enable.idempotence=true` | Producer 재시도로 인한 중복 방지 |
| 보관 | 3일 (2026-11-25 변경, 초안 7일) | Bronze 장애 시 따라잡을 여유. 장기 보관은 Bronze. KRW 전체·복제 3벌이면 3일 약 110GB, 7일 약 256GB (계산) |
| 압축 | `compression.type=zstd` | 호가 JSON이 커서(평균 약 2.7KB) 압축 효과가 큼 ([ADR-15](#adr-15-저장-압축과-보관)) |

**주의.** Producer 멱등성은 Kafka 내부 재시도 중복만 막습니다. WebSocket 재연결로 같은 체결을 다시 받는 경우는 막지 못하므로 최종 중복 제거는 Silver에서 `(market, sequential_id)`로 합니다.

## ADR-06. 대시보드 데이터 소스

| 대안 | 판단 |
|---|---|
| Grafana가 Delta를 직접 읽음 | Grafana에 내장 Delta 데이터 소스가 없음 |
| Spark Thrift Server로 SQL 제공 | 상시 Spark가 하나 더 필요, 무거움 |
| DuckDB로 Delta 조회 | Grafana 연동이 플러그인 의존 |
| **PostgreSQL에 최근 데이터 복제** | Grafana 기본 지원, 빠름, MLflow·Airflow 메타데이터 DB와 공유 가능 |

**결정.** Gold의 최근 30일 분량과 예측·채점 결과를 PostgreSQL에 upsert하고, Grafana는 PostgreSQL과 Prometheus만 읽습니다.
**바꿀 조건.** 대시보드에서 장기간 조회가 필요해지면 TimescaleDB 확장이나 별도 분석 엔진을 검토합니다.

## ADR-07. 화면 도구

화면은 보는 사람과 목적이 다르므로 둘로 나눕니다.

| 화면 | 보는 사람 | 목적 |
|---|---|---|
| 서비스 화면 | 사용자 | 코인별 급변동 위험도, 예측 vs 실제 |
| 운영 대시보드 | 운영자 | 파이프라인 지연·적체·공백, 대사 일치율, 모델 성능·드리프트 |

| 도구 | 일반적인 용도 | 판단 |
|---|---|---|
| **React + TypeScript 웹 + FastAPI** | 제품용 사용자 화면 | **서비스 대시보드 채택.** 실시간 갱신(WebSocket), 화면 구성의 자유도, API 계약(OpenAPI)으로 데이터 계층과 화면을 분리할 수 있음 |
| Streamlit | Python 데이터 앱, 내부 데모 | 탈락. 빠르게 만들 수 있지만 실시간 푸시와 화면 구성에 제약이 있고 제품 화면으로 쓰기 어려움 |
| **Grafana** | 시계열 지표 모니터링, 경보 | **운영 대시보드 채택.** Prometheus와 PostgreSQL을 기본 지원하고 경보 규칙을 붙일 수 있음 |
| Superset·Metabase | 분석가용 BI (SQL 기반 리포트) | 탈락. 분석 리포트 소비자가 따로 없음 |

**결정.** 서비스 대시보드는 FastAPI(`api/`) + React(`web/`), 운영 대시보드는 Grafana로 합니다. 화면용 데이터는 PostgreSQL `serve_*` 테이블과 Kafka 예측 토픽에서만 가져오므로, 화면을 바꿔도 데이터 계층은 그대로입니다.
**바꿀 조건.** 일정이 부족하면 React 화면을 줄이고 Grafana로 데이터를 확인합니다. 단계 순서는 [07 문서](07_단계별실행계획.md)를 따릅니다.

## ADR-08. 예측 모델

| 모델 | 판단 | 이유 |
|---|---|---|
| **LightGBM** | **메인** | 숫자 표 예측에 강한 기준선, CPU로 학습·예측이 빠름, 피처 중요도로 해석 가능 |
| 로지스틱 회귀 | 기준선 | 가장 단순한 학습 모델 |
| 규칙 기반 | 기준선 | ML 없이 어디까지 되는지 |
| LSTM 등 딥러닝 | 보류 | 데이터가 쌓이고 LightGBM 한계가 확인되면 비교 |
| Qwen 등 LLM | 예측에는 부적합 | 입력이 글이 아닌 숫자 표, 느림, 해석 어려움. 확장 단계에서 "해설 생성" 용도로만 검토 |

## ADR-09. 학습 방식

| 방식 | 판단 | 이유 |
|---|---|---|
| 온라인 학습 (데이터마다 모델 갱신) | 탈락 | 어떤 시점 모델이 무엇을 예측했는지 추적하기 어렵고, 이상 데이터에 망가질 수 있음 |
| **실시간 예측 + 주기적 재학습 (매일, 처음부터)** | **채택** | 모델 버전이 명확하고 되돌릴 수 있음. 기존 모델보다 나을 때만 교체 |
| 이어서 학습 (LightGBM `init_model`) | 탈락, 비교 실험만 선택 | 옛 패턴이 남고 정답 기준이 섞이며 추적·롤백이 어려움. 처음부터 해도 수 분이라 이득이 작음 ([05 문서 6.5절](05_ML_MLOps설계.md)) |

**바꿀 조건.** 일일 재학습으로 따라가지 못할 만큼 분포가 빨리 바뀌는 것이 채점 결과로 확인되면 재학습 주기를 줄입니다.

## ADR-10. 피처 저장

**결정.** Feast 같은 피처 스토어 없이, Gold 피처 테이블과 공용 피처 함수로 시점 정합성을 직접 보장합니다. 직접 구현해 봐야 피처 스토어가 무엇을 대신해 주는지 설명할 수 있습니다.
**바꿀 조건.** 피처가 많아지고 온라인 조회 지연이 문제가 되면 Feast를 도입합니다.

## ADR-11. 저장소

| 대안 | 판단 |
|---|---|
| **로컬 디스크** | L0 채택. 가장 단순 |
| **MinIO (S3 호환)** | ~~L1 채택~~ → 2026-11-26 취소. 무료판이 2025년 10월 공식 Docker 이미지 배포를 멈추고 12월 유지보수 모드로 들어가 이미지 기준(9-1절)을 통과하지 못함. PC 1대라 분산 저장의 이득도 없음 |
| HDFS | ~~탈락~~ → **2026-11-27 채택.** 운영 부담(NameNode·DataNode)을 감수하고 분산 저장을 실제 파이프라인으로 보여 줌 (09 3절) |

**주의 (2026-11-26 확인 결과 MinIO는 취소, 위 표).** MinIO 커뮤니티판의 라이선스(AGPL)와 배포 방식, 로컬 디스크 대신 쓸지는 운영·인프라 결정 때 다시 확인합니다(미정). 맞지 않으면 SeaweedFS, Garage 등 다른 S3 호환 저장소로 대체합니다. 또 Delta를 S3 호환 저장소에 둘 때 서로 다른 Spark 클러스터가 같은 테이블에 동시에 쓰는 것은 기본 설정으로 안전하지 않으므로 "테이블마다 쓰는 잡은 하나" 규칙을 둡니다.

## ADR-12. 클러스터 관리

**결정 (2026-11-27 변경).** 처음부터 Spark Standalone(master 1 + worker 2). 이전 결정은 L0 `local[*]`, L1 Standalone이었음. YARN은 Hadoop 클러스터가 있어야 의미가 있고, Kubernetes는 L2에서 검토합니다.
**주의.** PySpark는 Standalone의 cluster 배포 모드를 지원하지 않으므로, 드라이버 재시작은 Docker 재시작 정책이나 감시 스크립트가 맡습니다.

## ADR-13. 오케스트레이션

**결정 (2026-11-25 변경).** 일일 재계산·공식 캔들 대사·REST 공백 보충을 처음부터 Airflow DAG로 돌립니다. Airflow는 날짜 단위 멱등 실행과 backfill을 지원하고, 메모리 실측(PC 31.2GB 중 17.4GB 여유, [09 문서 M11](09_결정현황.md))으로 여유가 확인되어 바꿨습니다. 1단계 실측에서 메모리가 모자라면 cron으로 돌아갑니다. 이전 결정은 "DE 단계는 cron, Airflow는 나중"이었습니다. 처음부터 Airflow를 띄우면 메모리와 설정 부담이 커서 핵심 작업이 늦어집니다.
**바꿀 조건.** 작업 간 의존성과 재시도, 백필 관리가 cron으로 감당되지 않으면 그 시점에 Airflow를 도입합니다.

## ADR-14. 디지털 트윈 기획서 검토

**배경.** 외부 의견으로 「거시경제·금융 디지털 트윈 기반 AI 분석 및 트레이딩 시스템 기획서」를 고려 사항으로 받았습니다. 그 기획서를 새 주제로 삼을지, 일부만 가져올지 판단했습니다.

| 기획서 항목 | 판단 | 이 프로젝트에서의 형태와 이유 |
|---|---|---|
| Walk-forward 검증 | **채택** | 매일 재학습하는 운영 방식을 과거 데이터로 재현. 한 번의 분할 평가보다 믿을 수 있음 ([05 문서 5.1절](05_ML_MLOps설계.md)) |
| Ablation 테스트 | **채택** | 피처 묶음 켜고 끄기 A0~A4. 수집한 데이터가 예측에 쓸모 있었는지를 수치로 증명 |
| 금융 네트워크(GNN)의 관계 아이디어 | **축소 채택** | GNN 대신 마켓 간 관계 피처 4개. 그래프 모델 없이 같은 질문을 싸게 시험 |
| Calibration 평가 | **채택** | 신뢰도 곡선. 대시보드의 확률 값을 믿을 근거 |
| Observed / Estimated World 분리 | **이미 반영** | 관측(`fact_*`)과 모델 결과(`feat_*`, `prediction_*`)를 같은 테이블에 섞지 않음 |
| Event Time / Available Time, Vintage | **이미 반영** | `event_at` / `received_at`, Gold `revision`, 뉴스 확장의 `received_at` 규칙 |
| 상태 추정, Regime Flag | 선택 | HAR-RV 기준선(B2)과 "고변동 상태" 표시 |
| 시계열 사전학습 모델 (Chronos 등) | 선택 | M3 비교 후보 |
| 저비트 상태 압축 (INT8/INT4) | 기각 | 피처 수십 개, LightGBM 규모에서는 아낄 메모리·속도가 거의 없음. 용량 문제는 ADR-15로 해결 |
| Long/Short, Paper Trading | 기각 | "투자 도구가 아님" 정책과 충돌. 수익률 지표는 백테스트 과적합 논란이 생기기 쉬움 |
| Monte Carlo, SFC 시뮬레이션 | 기각 | 5분 변동성 문제에 필요 없음 |
| Graph DB, Vector DB, Redis | 기각 | 현재 규모에서 병목 없음 |
| 거시 데이터로 주제 전환 | 기각 | 월·분기 단위라 샘플이 적고 채점이 몇 달 걸려 MLOps 루프를 돌릴 수 없음. Spark·Kafka를 쓸 이유도 약해짐 |

**결정.** 주제(5분 급변동 확률 예측 + 주기적 재학습)는 유지하고, 위의 채택 항목만 반영합니다. 채택한 항목은 모두 새 인프라 없이 이미 쌓는 데이터 위에서 돌고, 결과가 수치로 남는다는 공통점이 있습니다.
**바꿀 조건.** 이 프로젝트를 마친 뒤 거시 데이터를 다룬다면, ALFRED vintage 기반 데이터 원장 + BVAR 예측 정도로 범위를 줄인 별도 프로젝트로 시작합니다.

## ADR-15. 저장 압축과 보관

**근거.** 2026-11-24 실측(상위 10개 마켓, 120초): 하루 원본 약 11GB, gzip 압축 후 약 1GB이며 **약 95%가 호가**(30단계, 평균 약 2.7KB)입니다. ([03 문서 5.1절](03_시스템아키텍처.md))

| 대안 | 판단 | 이유 |
|---|---|---|
| 압축 없이 전부 장기 보관 | 탈락 | 1년이면 수 TB 규모가 될 수 있고, L1 Kafka 복제 3벌이면 더 커짐 |
| 값 자체를 줄이기 (저정밀 저장) | 탈락 | 가격·거래량이 정확해야 공식 캔들 대사가 가능함 |
| **파일 압축 + 보관 기간** | **채택** | Kafka zstd, Delta/Parquet zstd 코덱. 호가 원본은 Bronze에 90일 보관. Silver에는 호가 요약 컬럼만 저장 |
| 호가를 1초 간격으로 솎아서 저장 | 보류 | 원본 보관 원칙과 충돌. 90일 정책으로 부족할 때 검토 |

**변경 (2026-11-25).** 호가 원본 90일 보관은 ADR-16에 따라 "2주 수집분 전부 보관"으로 바뀌었습니다. 파일 압축 방식은 그대로입니다.

**주의.** `VACUUM`으로 오래된 파일을 지울 때 학습셋 스냅샷이 참조하는 Delta 버전은 지우지 않도록 보존 기간을 설정합니다. 또 90일이 지난 호가로는 새 호가 피처를 다시 계산할 수 없으므로, 새 호가 피처는 90일 안의 데이터로만 실험합니다.
**바꿀 조건.** 1단계 실측 디스크 사용량이 추정의 3배를 넘거나 SSD 여유가 30% 아래로 떨어지면 보관 기간을 줄이거나 솎아 저장을 도입합니다.

## ADR-17. Git 운영: `main` 하나

**이전 결정 (2026-11-25).** 측정·코드처럼 결과가 들어가는 작업은 이슈 → 브랜치 → PR → CI → Merge commit.

**바뀐 결정 (2026-11-26, 사용자 지시).** 모든 작업을 `main`에서 하고 브랜치·PR을 만들지 않습니다. Dependabot이 만드는 업데이트 PR만 예외입니다.

**이유.** 1인 프로젝트라 리뷰할 사람이 없고, 브랜치·PR은 단계마다 절차만 늘립니다. 브랜치로 지키려던 "측정 결과가 어느 코드에서 나왔나"는 원장의 `git_sha` 열과 코드 커밋과 따로 두는 `record` 커밋으로 그대로 추적됩니다.

**대가.** `main`에 잘못된 커밋이 들어가도 막는 장치가 없습니다(비공개 무료 요금제는 브랜치 보호 불가). 그래서 push 전에 `./verify.sh`를 통과시키고 push 뒤 CI 결과를 확인합니다.

**바꿀 조건.** 함께 작업하는 사람이 생기면 브랜치·PR로 돌아갑니다.
