# 09. 결정 현황

설계 결정을 한곳에서 관리하는 문서입니다. **01~08 문서와 내용이 다르면 이 문서가 우선합니다.** 01~08은 이 문서에 맞춰 순서대로 고칩니다.

- 최종 갱신: 2026-11-26 (M12 추가)
- 상태 표기: **확정** = 그대로 구현 / **제안** = 방향은 잡혔으나 확정 전 / **미정** = 측정·실험 후 결정
- 근거 표기: 실측 = 직접 측정 / 계산 = 실측값으로 계산 / 공식 = 업비트 등 공식 자료 / 미검증 = 아직 확인 안 함

## 1. 목표

| 항목 | 내용 | 상태 |
|---|---|---|
| 목표 | 업비트 실시간 데이터를 끊김 없이 모으는 파이프라인을 만들고, 그 데이터로 코인별 "다음 5분에 평소보다 크게 움직일 확률"을 1분마다 예측하고, 5분 뒤 자동 채점하고, 주기적으로 재학습한다 | 확정 |
| 예측하지 않는 것 | 가격 방향(오를지 내릴지). 근거는 10절 M1 | 확정 |
| 구현 순서 | **DE(실시간 파이프라인: 수집 → Bronze → Silver → Gold)를 먼저 만들고, ML은 그 뒤에 진행한다.** 과거 데이터도 ML 단계에서 받는다 | 확정 |
| 프로젝트 흐름과 종료 | DE 구축 → **실시간 2주 운영** → 그 2주 실시간 데이터로 ML 예측이 되는지 확인 → 문서 정리 → **프로젝트 종료**. 2주 운영 뒤 수집을 계속하지 않음 | 확정 |
| ML 항목 재검토 | 6~9절(과거 데이터, 라벨, 평가, 모델·재학습)은 2주 운영 계획 이전에 정한 것. **ML 단계 시작 전에 2주 데이터 기준으로 다시 검토**하고, 그 전까지 DE 구현에는 반영하지 않음 | 확정 |
| DE 목표 | **실시간 수집을 2주(14일) 연속 운영하면서 모니터링으로 상태를 수치로 보여준다.** 보여줄 것: 유실(공백 구간, 빠진 분 수), 중복(`sequential_id` 중복 건수), 정확성(공식 캔들 일치율), 지연(수신→저장 p95), 장애 회복(구성요소를 끄고 켜는 시험). 합격 기준값은 미정 | 확정 (기준값 미정) |
| DE 구현 순서 | ① 수집기 → Kafka ② Kafka → Bronze ③ Prometheus + Grafana ④ Bronze → Silver ⑤ Silver → Gold ⑥ Gold → PostgreSQL `serve_*` (DE용: 캔들, 호가 요약, 마켓 목록, 일치율) ⑦ FastAPI → React. Grafana를 ③에 두는 이유: 수집 첫날부터 지켜봐야 2주 기록이 남음 | 확정 |
| 2주 시작 | **1~5단계가 모두 돌고 경보 시험을 마친 날부터 14일.** 만드는 동안 받은 데이터는 개발용이라 시작 전에 삭제. 14일 동안 코드는 버그 수정만 하고 언제·무엇을·왜 고쳤는지 기록 | 확정 (2026-11-25) |
| 2주 합격 기준 항목 | 네 가지 모두 넣고 역할을 나눔. **핵심(통과·실패 판정)**: ① 유실·중복 (수집기가 하나라도 살아 있던 구간의 체결 유실 0건, 유실은 공식 캔들 대사로 판정 / Silver 중복 0건) ② 공식 캔들 일치율 (공식 캔들이 있는 분 기준, 전체와 마켓×1시간 칸 최소값). **보조(측정값 보고, 시험은 시험별 판정)**: ③ 지연 p95와 경보 도착 시간 ④ 장애 시험 통과와 복구 시간. 이유: 핵심 두 개가 "유실·중복 없이, 맞는 값을 받는다"는 첫 주장이고, 지연은 처리 주기 설정에 따라 달라지는 값이라 아깝게 넘어도 2주 전체가 실패처럼 보이면 안 됨 | 확정 (2026-11-25) |
| 호가 판정 범위 | 유실 0 판정은 **체결에만** 적용. 호가는 대조할 공식 기준이 없어 호가가 비어 있던 시간(공백 창)의 횟수와 총 분을 숫자로 보고만 함 | 확정 (2026-11-25) |
| 기준 숫자 | 개발 기간에 실제로 잰 값을 근거로 **2주 시작 전에 고정**. 결과를 본 뒤에는 바꾸지 않음 | 확정 (2026-11-25) |
| 2주 중 큰 장애 | 14일을 그대로 이어가고 장애 보고서(원인, 영향, 복구 시간, 재발 방지)를 씀. 다시 시작하지 않음 | 확정 (2026-11-25) |
| 연속의 뜻 | 14일(달력 기준) 동안 생긴 공백이 빠짐없이 기록되고 원인이 설명되면 통과. 공백 횟수와 총 분은 숫자로 보고. **계획 정지**(사용자가 PC를 꺼야 할 때)도 허용: 끄기 전에 정지 절차(수집기 버퍼 비우기, Spark 체크포인트 정리)를 실행하고 시작·끝·이유를 기록, 켜지면 자동 기동. 체결은 REST 재수집이 되면 보충, 호가는 그 기간 손실 | 확정 (2026-11-25) |
| 경보 채널 | **Discord** (Grafana 경보 → Discord 웹훅). 웹훅 주소는 사용자가 직접 `.env`에 넣음 | 확정 (2026-11-25) |
| 저장 위치 | 원본·정제·학습 데이터는 모두 Delta (Bronze → Silver → Gold → `train_dataset` 스냅샷). PostgreSQL은 화면용 최근 복사본만, Grafana는 시스템·품질 지표 화면 | 확정 |
| 결정 시점 | 미정 항목은 그 항목을 쓰는 단계를 시작하기 전에 정한다. 단, Bronze 원본으로 다시 계산할 수 없는 것(무엇을 수집하나, 원본을 얼마나 보관하나)은 수집 시작 전에 정한다 | 확정 |

## 2. 수집

| 항목 | 내용 | 상태 |
|---|---|---|
| 수집 범위 | KRW 마켓 전체 (체결, 호가, 현재가, 마켓 목록) | 확정 |
| 현재가 | 수집함. 거래 정지(`is_trading_suspended`)와 상장 폐지 예정일(`delisting_date`)은 현재가에만 있음. 압축 후 하루 약 0.29GB (10절 M8) | 확정 |
| 수집기 | 2대 동시 수집. 중복은 하류에서 `sequential_id`로 제거 | 확정 |
| 업비트 연결 | 수집기 1대당 **종류별 연결 3개** (체결, 호가, 현재가 각각 KRW 전체). 2대면 6개. 호가가 느려지거나 끊겨도 다른 종류에 영향 없음. 한 구독에 넣을 수 있는 코인 수 제한은 문서에 없어 0단계에서 확인 | 확정 (2026-11-25) |
| 상장·폐지 반영 | 각 수집기가 5분마다 REST 마켓 목록을 **직접** 확인하고, 바뀌었을 때만 같은 연결에 새 코인 목록으로 구독 메시지를 다시 보냄(연결은 유지). 바꾸는 순간 빈틈이나 SNAPSHOT 중복이 생기는지는 0단계에서 확인 | 확정 (2026-11-25) |
| 연결 끊김 | 공백 구간을 기록하고 REST 1분 캔들로 보충 | 확정 |
| Kafka | 브로커 3대. 보관 **3일** (복제 3벌 기준 약 110GB, 계산). Bronze 저장이 멈춰도 주말 동안은 따라잡을 수 있음. 원본은 Bronze에 전부 남음. **파티션**: 체결·호가·현재가 토픽 3칸, 마켓 목록·공백 기록 토픽 1칸. 처리량 때문이 아니라 브로커 3대가 1칸씩 대표를 맡고 브로커 장애 시험(T12)이 의미 있게 하려는 것. 칸은 늘릴 수만 있으므로 2주 동안 바꾸지 않음 | 확정 (2026-11-25) |
| Spark | 처음에는 1개로 시작하고 3단계부터 클러스터 구성 | 제안 (운영 파트에서 확정) |

## 3. Bronze

| 항목 | 내용 | 상태 |
|---|---|---|
| 저장 형식 | 받은 JSON 원본 그대로 + Kafka 위치(topic, partition, offset) | 확정 |
| 호가 원본 | 30줄 원본을 전부 보관 (삭제 규칙 없음). 디스크 여유 30%까지 약 59일 (계산, Kafka 3일 보관 기준)이라 2주 운영 동안 지울 필요 없음. ADR-15의 "90일 보관"은 상위 10개 기준 값이라 쓰지 않음 (ADR-16) | 확정 |
| 보관 방법 | 2주 수집분 전부(체결·현재가·호가·마켓 목록)를 PC SSD에 그대로 둠. 외장 디스크로 옮기거나 삭제하지 않음. 체결·현재가는 1년치도 약 139GB (계산)라 지울 이유가 없음 | 확정 |
| 2주 운영 시 디스크 | **수집기 1대분 계산이라 다시 계산 필요 (11.1절 D7, M12).** Bronze 약 171GB + Silver 약 14GB + Kafka 약 110GB(3일) = 약 295GB. 여유 1,444GB(실측) 중 약 1,149GB 남음, 전체의 약 62% (계산). 2주 동안은 Bronze를 지울 필요 없음 | 참고 |
| 디스크 경보 | 디스크 여유가 30% 아래로 내려가면 경보. 2주 운영에서는 닿지 않을 것으로 계산되지만, 측정값이 추정과 다를 때를 대비한 안전장치 | 제안 |

## 4. Silver

| 항목 | 내용 | 상태 |
|---|---|---|
| 시각 | UTC로 저장하고, 화면에서만 한국 시간으로 표시 | 확정 |
| 불량 데이터 | 품질 규칙 위반 행은 격리 테이블로 보내고 처리는 계속함 | 확정 |
| 중복 기록 | 제거한 중복은 키와 Kafka 위치만 기록 | 확정 |
| 건수 대사 | Bronze 건수 = Silver + 격리 + 중복 | 확정 |
| 규칙 파일 | 품질 규칙과 데이터 사전을 별도 파일(YAML 등)로 두고 검증에 사용 | 확정 |
| 호가 요약 | 구간 요약(D안): 1줄, 1~5줄 합, 6~10줄 합, 11~20줄 합, 21~30줄 합 + 스프레드, 매수·매도 쏠림, 30줄까지의 가격 폭, 가장 큰 주문 한 줄의 크기와 위치. 호가 메시지 1개 = Silver 1행 (Bronze와 행 수 같음, 30줄을 행으로 펼치지 않음) | 확정 |
| 요약의 한계 | 요약은 되돌릴 수 없음. Silver로 Bronze 30줄을 복구할 수 없고, 요약 방식을 바꾸려면 Bronze 원본으로 다시 계산해야 함. 따라서 ML 피처를 정하기 전에는 Bronze 호가 원본을 지우지 않음 | 확정 |

## 7. 예측 대상과 라벨

| 항목 | 내용 | 상태 |
|---|---|---|
| 예측 범위 | **KRW 전체 코인을 1분마다 예측.** 대상에서 빠지는 코인이 없으므로 평소 조용하던 코인의 급변동도 놓치지 않음 | 확정 |
| 이전 안 폐기 | "거래대금 상위 N개 자동선정"은 쓰지 않음. N에 근거가 없고, 대상 밖 코인의 급변동을 놓침 | 확정 |
| 라벨 | 코인별 "다음 5분 변동폭 (최고가 − 최저가) ÷ 종가"가 그 코인 기준값 이상이면 1 | 확정 |
| 기준값 | 상위 20%(80번째 백분위수). 상위 10%도 함께 평가. 학습 기간 데이터로만 계산 | 제안 |
| 유효 구간 | 5분 안에 거래가 k건 이상인 구간만 라벨을 만들고 채점함. 거래가 없는 구간은 라벨 없음 (10절 M5) | 확정 |
| 기준값 계산 범위 | 유효 구간만으로 계산. 전체 구간으로 계산하면 거래가 적은 코인은 기준값이 0.00%가 됨 (10절 M5) | 확정 |
| k | 과거 데이터의 검증 기간에서 정하고, 최종 평가 기간에는 고정 | 미정 |
