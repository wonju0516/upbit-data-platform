## 2. 수집

| 항목 | 내용 | 상태 |
|---|---|---|
| 수집 범위 | KRW 마켓 전체 (체결, 호가, 현재가, 마켓 목록) | 확정 |
| 현재가 | 수집함. 거래 정지(`is_trading_suspended`)와 상장 폐지 예정일(`delisting_date`)은 현재가에만 있음. 압축 후 하루 약 0.29GB (10절 M8) | 확정 |
| 수집기 | ~~2대 동시 수집~~ → **1대 (임시, 11.1절 D7)**. 중복은 하류에서 `sequential_id`로 제거 | 임시 (2026-11-26) |
| 업비트 연결 | 수집기 1대당 **종류별 연결 3개** (체결, 호가, 현재가 각각 KRW 전체). 2대면 6개. 호가가 느려지거나 끊겨도 다른 종류에 영향 없음. 한 구독에 넣을 수 있는 코인 수 제한은 문서에 없어 0단계에서 확인 | 확정 (2026-11-25) |
| 상장·폐지 반영 | 각 수집기가 5분마다 REST 마켓 목록을 **직접** 확인하고, 바뀌었을 때만 같은 연결에 새 코인 목록으로 구독 메시지를 다시 보냄(연결은 유지). 바꾸는 순간 빈틈이나 SNAPSHOT 중복이 생기는지는 0단계에서 확인 | 확정 (2026-11-25) |
| 수집기 죽음·멈춤 (자동 재시작) | **수집기는 Docker 컨테이너로 돌리고 재시작 정책 `unless-stopped`를 둔다.** 프로세스가 끝나면(오류, 강제 종료) Docker가 바로 다시 띄우고, PC가 다시 켜지면 Docker Desktop 자동 시작(사용자 설정, 2026-11-27)과 함께 뜬다. 사람이 직접 멈춘 것은 다시 띄우지 않는다(Docker 공식 문서). 재시작 정책은 프로세스가 **끝나야** 동작하므로, 먹통(멈춤)은 수집기 안의 감시가 잡는다: 상태 저장이 60초 넘게 멈추면 스스로 종료 → Docker가 다시 띄움. 컨테이너에 작은 init(`init: true`)을 둬 종료 신호가 수집기에 제대로 전달되게 한다. 다시 뜨면 마지막 수신 시각부터를 공백(`PROCESS_RESTART`)으로 남기고 `restart_cause`에 이유를 적는다: `CRASH`(이유를 남기지 못하고 꺼짐: 오류·강제 종료·정전), `HANG`(감시가 끝냄), `PLANNED`(사람이 멈춤, `PLANNED_STOP`). 체결은 REST로 보충. **침묵 감지와 다른 점**: 침묵 감지는 수집기가 살아 있는 채로 연결 하나에 10초 동안 데이터가 없을 때 그 연결만 다시 붙이는 것이고(`SILENCE`), 자동 재시작은 수집기 전체가 죽거나 멈췄을 때 프로그램을 다시 띄우는 것. 다른 방법(WSL systemd, Windows 서비스, Kubernetes)은 재부팅 뒤 복구가 불확실하거나 Kafka와 관리 방식이 갈라지거나 1대에 과해 쓰지 않음. 검증: T06·T18 통과(06 문서) | 확정 (2026-11-27) |
| 연결 끊김 (공백 처리) | **빈틈 없는 수집을 목표로 하지 않고, 빈 곳을 정확히 기록하고 되살릴 수 있는 것만 되살린다.** ① 체결: REST 체결 이력으로 보충(9-2절 C, M14 100%) ② 호가·현재가: 되살릴 방법이 없어 공백 표시만 ③ **연결 공백**(수집기가 끊김·침묵을 감지한 구간)과 **종목 무수신**(연결은 살아 있는데 그 종목 거래가 없음)을 구분하고, 종목 무수신은 공백이 아님 ④ 공백 기록은 수집 첫날부터 `ops.ingest_gap`에 남김(나중에 추가하면 조용했던 구간과 끊긴 구간을 구분할 수 없음) ⑤ 호가 이중화는 ML에서 호가 피처가 성능을 실제로 올리는지 확인한 뒤 다시 검토. 근거: 물결 1번에 24~32초 침묵(M13, 실측), 2주 동안 50번이라 가정해도 약 1,500초 = 약 0.12%(계산, 횟수는 가정) | 확정 (2026-11-26) |
| Kafka | 브로커 3대. 보관 **3일** (복제 3벌 기준 약 110GB, 계산). Bronze 저장이 멈춰도 주말 동안은 따라잡을 수 있음. 원본은 Bronze에 전부 남음. **파티션**: 체결·호가·현재가 토픽 3칸, 마켓 목록·공백 기록 토픽 1칸. 처리량 때문이 아니라 브로커 3대가 1칸씩 대표를 맡고 브로커 장애 시험(T12)이 의미 있게 하려는 것. 칸은 늘릴 수만 있으므로 2주 동안 바꾸지 않음 | 확정 (2026-11-25) |
| Spark | 처음에는 1개로 시작하고 3단계부터 클러스터 구성 | 제안 (운영 파트에서 확정) |

## 3. Bronze

| 항목 | 내용 | 상태 |
|---|---|---|
| 저장 형식 | 받은 JSON 원본 그대로 + Kafka 위치(topic, partition, offset) | 확정 |
| 호가 원본 | 30줄 원본을 전부 보관 (삭제 규칙 없음). 디스크 여유 30%까지 약 59일 (계산, Kafka 3일 보관 기준)이라 2주 운영 동안 지울 필요 없음. ADR-15의 "90일 보관"은 상위 10개 기준 값이라 쓰지 않음 (ADR-16) | 확정 |
| 보관 방법 | 2주 수집분 전부(체결·현재가·호가·마켓 목록)를 PC SSD에 그대로 둠. 외장 디스크로 옮기거나 삭제하지 않음. 체결·현재가는 1년치도 약 139GB (계산)라 지울 이유가 없음 | 확정 |
| 저장소 | **PC 로컬 디스크(SSD)에 Delta Lake로 저장.** PC가 1대라 분산 저장은 디스크 고장을 막지 못해 의미가 없고, 원본 보호는 아래 집 밖 S3 백업으로 함. 처음엔 MinIO 분산 4대로 정했으나 다시 확인해 보니 MinIO 무료판이 2025년 10월 공식 Docker 이미지 배포를 멈추고 12월 유지보수 모드로 들어가(보안 수정도 보장 안 함, 공개 기사 기준) 9-1절 이미지 기준(많이 쓰는 안정판 + 보안 문제 없음)을 통과하지 못함. 구성요소가 하나 줄고 디스크도 2배로 쓰지 않음 | 확정 (2026-11-26 사용자 선택, MinIO에서 변경) |
| 원천 백업 | **Bronze만 매일 AWS S3로 올림** (Airflow 작업, `aws s3 sync`). 올리기만 하고 읽지 않아 내려받기 요금이 거의 없음. 자주 꺼내지 않는 등급(Standard-IA)이면 220GB에 월 약 $3 (계산, 요금은 공식 요금표로 다시 확인). 집 밖 사본이라 디스크 고장·화재·도난에도 남음. Silver·Gold는 Bronze로 다시 만들 수 있어 백업하지 않음. AWS 계정·키는 사용자가 직접 만들고 입력하며 요금 알림을 설정. 할 일: 업비트 약관상 비공개 클라우드 보관이 문제없는지 확인 | 확정 (2026-11-26 사용자 "백업용으로 올린다"), 약관 확인 전 |
| 2주 운영 시 디스크 | **수집기 1대분 계산이라 다시 계산 필요 (11.1절 D7, M12).** Bronze 약 171GB + Silver 약 14GB + Kafka 약 110GB(3일) = 약 295GB. 여유 1,444GB(실측) 중 약 1,149GB 남음, 전체의 약 62% (계산). 2주 동안은 Bronze를 지울 필요 없음 | 참고 |
| 디스크 경보 | 디스크 여유가 30% 아래로 내려가면 경보. 2주 운영에서는 닿지 않을 것으로 계산되지만, 측정값이 추정과 다를 때를 대비한 안전장치 | 제안 |

## 5. Gold

## 7. 예측 대상과 라벨

| 기준값 계산 범위 | 유효 구간만으로 계산. 전체 구간으로 계산하면 거래가 적은 코인은 기준값이 0.00%가 됨 (10절 M5) | 확정 |
