# 10. 한계

이 프로젝트로 **말할 수 없는 것**과 알고 받아들인 제약을 모읍니다. 설계 단계에서 이미 알고 있는 것만 적었고, 운영과 ML 결과가 나오면 갱신합니다. 근거가 되는 결정은 [09_결정현황.md](09_결정현황.md)에 있습니다.

## 1. 운영 구조

| 한계 | 이유 | 근거 |
|---|---|---|
| 가용성이 없음 | PC 1대 안의 컨테이너입니다. 수집기 2대와 Kafka 3대는 프로세스 장애만 막고, PC·전원·디스크 장애는 막지 못합니다 | 09 2절, 03 문서 6절 |
| 인터넷이 끊기면 수집기 2대가 같이 끊김 | 같은 집 인터넷을 씁니다. 체결은 REST로 다시 받을 수 있는지 확인 예정이고, 호가는 메울 수 없습니다 | 09 9-2절 C |
| Kafka 복제 3벌도 같은 디스크 | 브로커 장애는 견디지만 디스크 고장은 못 견딥니다 | 09 2절 |
| 백업 없음 | 개인 프로젝트라 하지 않기로 했습니다. SSD가 고장 나면 그 기간 데이터를 잃습니다 | 09 9-1절 |
| 복구는 수동 | 경보는 오지만 사람이 직접 고칩니다 | 09 1절 |

## 2. 규모와 기간

| 한계 | 이유 | 근거 |
|---|---|---|
| 대용량 처리를 말할 수 없음 | KRW 전체를 받아도 초당 수십~수백 건 수준입니다 (체결 초당 24.8건, 현재가 35.7건, 60초 표본) | 09 M8 |
| 운영 기간 2주 | 장기 운영에서만 보이는 문제(계절성, 장기 디스크 증가, 드문 장애)는 확인할 수 없습니다 | 09 1절 |
| 분산 처리 경험이 아님 | Spark는 한 PC 안에서 돕니다 | 09 2절 |

## 3. 데이터

| 한계 | 이유 | 근거 |
|---|---|---|
| 상장 폐지 코인이 빠짐 (생존 편향) | 업비트 REST로 폐지 코인 과거 데이터를 받을 수 없습니다 | 09 M4 |
| 호가 공백은 영구 손실 | 업비트에 과거 호가를 다시 받는 API가 없습니다 | 09 9-2절 B |
| 데이터셋을 공개할 수 없음 | 데이터 저작권이 두나무에 있습니다. 다른 사람이 같은 데이터로 결과를 재현하려면 직접 수집해야 합니다 | 09 M10 |
| 공개 범위 일부 미확인 | 비상업 개인 분석과 요약 지표 공개를 다루는 약관 조항이 없습니다. 법률 판단을 받지 않았습니다 | 09 M10 |
| 용량·처리량 수치는 짧은 표본 기반 | 60초~2분 표본에서 계산한 값입니다. 1단계에서 며칠치로 다시 잽니다 | 09 M8 |

## 4. ML

| 한계 | 이유 | 근거 |
|---|---|---|
| 학습 데이터가 2주뿐 | 호가·체결 피처를 쓸 수 있는 기간이 실시간 2주입니다 | 09 1절 |
| 예측 성능 주장 불가 | 목표는 파이프라인 운영이고, ML은 기준선 대비 확인입니다 | 09 1절 |
| 투자 판단에 쓸 수 없음 | 방향을 예측하지 않고, 수익률을 주장하지 않습니다 | 09 1절 |

## 5. 기타

| 한계 | 이유 |
|---|---|
| 실제 사용자 요구가 없음 | 소비자가 저 자신입니다 |
| 비슷한 공개 프로젝트가 더 오래 운영됨 | 같은 문제를 다룬 공개 프로젝트가 221일 운영 기록을 가지고 있습니다. 이 프로젝트의 차이는 Spark + Delta 계층 구조, 수집기·Kafka 이중화와 장애 시험, KRW 전체 호가 30줄 원본 보관, 2주 데이터 ML 확인입니다 |
